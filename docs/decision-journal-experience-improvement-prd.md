# 回看体验稳固与复盘增强：需求开发文档

**版本**：1.0  
**日期**：2026-08-04  
**参与角色**：产品经理、资深 Android 工程师 A（数据与架构）、资深 Android 工程师 B（Compose 与交互）  
**文档状态**：待开发  
**适用项目**：`decision-journal`

## 1. 文档目标

本文件将当前“回看”产品的体验评审结论转化为可执行的开发需求。目标不是继续扩展功能，而是先修复影响数据可信度、首次使用、保存反馈和长期复盘的关键问题，形成稳定的 MVP 闭环。

核心产品承诺：

> 帮用户记住当时为什么这样选，并在未来看见自己的判断。

本期完成后，用户应能在低负担的情况下记录一个决定，可靠地修改和保存它，在未来收到提醒并完成复盘，同时始终保留原始决策内容。

## 2. 当前基线与问题确认

当前项目已具备：

- Kotlin + Jetpack Compose + Material 3 + Room + Hilt + Navigation + WorkManager 技术栈。
- 今天、决定、我的三个主页面。
- 决策、候选选项、复盘的本地持久化。
- 多候选项、最终选择、复盘日期、多次复盘和满意度。
- 详情页编辑、删除确认和复盘入口。

本期需要解决的已确认问题：

| 编号 | 问题 | 影响 | 优先级 |
|---|---|---|---|
| P-01 | 编辑已复盘决定时统一写入 `ACTIVE` | 历史状态被错误改写，破坏用户信任 | P0 |
| P-02 | Debug 首次启动自动注入演示数据 | 空状态、首次引导和验收场景失真 | P0 |
| P-03 | 保存没有 Saving/Success 状态 | 用户无法确认是否保存成功，重复点击风险 | P0 |
| P-04 | 创建第一步字段过多 | 首次记录成本高，容易中途退出 | P1 |
| P-05 | 已添加候选项不能编辑 | 用户修改记录时被迫删除重建 | P1 |
| P-06 | “决定”和“我的”职责相近 | 信息架构理解成本高 | P1 |
| P-07 | 复盘页缺少明显返回入口，满意度为文本输入 | 导航和交互不够符合移动端习惯 | P1 |
| P-08 | 详情页没有突出“预期 vs 实际” | 复盘价值没有被清晰呈现 | P1 |
| P-09 | 缺少 Loading、Error、保存成功等完整状态 | 异常场景不可控 | P1 |
| P-10 | 长期记录缺少搜索和筛选 | 数据量增长后查找效率下降 | P2 |

## 3. 三方讨论结论

### 3.1 产品经理观点

1. 本期优先保障“记录可信”和“复盘闭环”，暂不引入 AI、云同步、社交和复杂图表。
2. 创建流程必须允许用户先快速记录，再逐步补充深度信息。
3. “我的”应该承担自我统计和洞察，“决定”应该承担检索全部记录，不能只是重复一条时间线。
4. 统计内容必须显示证据范围，避免把简单频次统计包装成过度智能的结论。

### 3.2 资深工程师 A：数据与架构观点

1. `Decision.status` 必须由明确的状态规则维护，不能在所有保存路径中硬编码为 `ACTIVE`。
2. 编辑决策时需要保留 `createdAt`、历史复盘和原始字段；候选项重建必须保证 `selectedChoiceId` 重新映射到新插入的 Choice ID。
3. 保存操作必须具备幂等保护；提醒任务使用同一个 decision ID 作为唯一 WorkManager name。
4. UI 不应直接推断业务状态；Repository/ViewModel 应输出显式的 `ScreenState` 和 `SaveState`。

### 3.3 资深工程师 B：Compose 与交互观点

1. 创建页继续使用三步向导，但第一步只保留问题和背景，其他字段移动到后续步骤的可选区域。
2. 保存按钮需要绑定 `Saving` 状态，保存期间禁用并显示进度，成功后只触发一次导航。
3. 候选项应使用可编辑卡片；本期不强制实现拖拽排序，但必须保留明确的顺序字段和后续扩展空间。
4. 通知权限不应在首次启动时打断用户，应在用户首次设置未来复盘日期时解释用途并请求。

### 3.4 争议与最终决策

| 议题 | 讨论结果 | 最终决策 |
|---|---|---|
| 是否立即重做底部导航 | 重做会扩大范围，当前重复问题可通过职责和文案缓解 | 本期保留三栏；“决定”增加筛选/搜索入口，“我的”只保留统计与洞察 |
| 是否支持草稿 | 草稿需要额外数据状态和恢复策略 | 本期不做自动草稿；返回未保存时给出确认提示 |
| 是否实现拖拽排序 | 价值存在但不是闭环阻塞项 | 本期提供上移/下移或编辑顺序，拖拽列为 P2 |
| 是否保留全部高级字段 | 字段对复盘有价值，但不应全部阻塞首条记录 | 保留数据字段，改为可选展开，不增加必填项 |
| 是否加入统计图表 | 数据量和验证不足 | 本期只做可解释的数字和文字统计 |

## 4. 目标用户与使用场景

### 4.1 主要用户：认真记录重要决定的人

- 目标：留下当时的判断依据，未来复盘自己是否看对、做对。
- 典型场景：换工作、搬家、购买大件、开始副业、关系选择、旅行计划。
- 痛点：事后只记得结果，忘记当时的信息和限制；复盘时容易用结果倒推当时的自己。
- 关键要求：低打扰、隐私、本地可用、原始内容不被改写。

### 4.2 资深用户：持续积累决策样本的人

- 目标：比较多次决策，发现自己的判断模式和重复担忧。
- 痛点：记录数量增加后查找困难，无法清楚比较预期与实际。
- 关键要求：可检索、可筛选、时间语义清晰、统计有证据来源。

## 5. 本期范围与非目标

### 5.1 本期范围

1. 修复编辑状态和关联数据一致性。
2. 移除正式运行中的自动演示数据注入。
3. 引入页面状态和保存状态。

## 6. 功能需求

### FR-001 决策状态保持与状态规则（P0）

#### 业务规则

| 场景 | 保存后的状态 |
|---|---|
| 新建决策 | `ACTIVE` |
| 编辑未复盘决策 | 保留原状态，通常为 `ACTIVE` |
| 编辑已复盘且无新复盘日期 | 保留 `REVIEWED` |
| 复盘后未设置下一次日期 | `REVIEWED` |
| 复盘后设置下一次日期 | `ACTIVE` |
| 删除决策 | 删除实体、候选项、复盘和提醒 |

#### 验收标准

- [ ] 编辑 `REVIEWED` 决策后，状态仍为 `REVIEWED`。
- [ ] 编辑问题、背景或候选项不会删除已有复盘记录。
- [ ] 复盘时设置下一次日期后，状态变为 `ACTIVE`。
- [ ] 复盘时不设置下一次日期后，状态变为 `REVIEWED`。
- [ ] 首页待复盘查询只展示日期到期且状态不是 `REVIEWED` 的记录。

### FR-002 正式包与演示数据隔离（P0）

- Debug 和 Release 均默认使用空数据库启动。
- 如需演示数据，必须通过开发者入口或测试 fixture 显式加载。
- 演示数据不得影响真实空状态验收。
- 首次启动不得自动创建决策、复盘或提醒。

验收标准：清除应用数据后启动，首页显示空状态；点击创建前数据库中没有决策和提醒。

### FR-003 创建流程降负（P1）

创建流程保持三步：

1. **先想清楚**：问题必填，背景可选。
2. **比较选择**：至少一个候选选项；每个选项支持利好和担忧，可选。
3. **未来再看**：复盘日期、未来寄语、预期结果、判断信心均可选。

规则：

- 问题去除首尾空白后至少 1 个字符。
- 至少一个候选项去除空白后有效。
- 未来寄语最多 500 个字符。
- 判断信心为空或 1～5 的整数。
- 离开存在未保存内容的页面时，弹出“放弃本次编辑？”确认。
- 返回上一步不得丢失已输入内容。

验收标准：新用户只填写问题、一个选项即可完成保存；高级字段为空不阻塞；非法输入显示字段级提示。

### FR-004 候选项编辑与顺序（P1）

- 已添加候选项显示“编辑”和“删除”操作。
- 编辑时预填选项名称、利好和担忧。
- 删除当前最终选择时，只清空最终选择，不自动选择其他项。
- 本期提供上移/下移操作；保存后 `position` 从 0 连续递增。
- 候选项名称为空时禁止保存该项。

验收标准：用户可修改任意候选项；重新排序后详情页和编辑页顺序一致；删除选中项后没有错误引用。

### FR-005 保存状态与错误反馈（P0/P1）

统一定义：

```text
SaveState = Idle | Saving | Success | Error(message)
ScreenState<T> = Loading | Empty | Content(T) | Error(message)
```

要求：

- 点击保存后立即进入 `Saving`，按钮禁用并显示进行中状态。
- Repository 成功后只触发一次导航。
- 重复点击不能产生重复决策、重复复盘或重复提醒。
- 数据库错误、提醒安排错误和校验错误都必须显示用户可理解的提示。
- 详情、列表和首页至少覆盖 Loading、Empty、Content、Error 四种状态。
- 保存成功反馈不依赖网络。

### FR-006 返回与删除交互（P1）

- 创建页、详情页、复盘页均提供明确的顶部返回按钮。
- Android 系统返回和手势返回行为与顶部返回一致。
- 有未保存内容时返回需要确认；无修改时直接返回。
- 删除必须二次确认。
- 删除成功后返回来源列表，不允许回到已删除详情页。
- 删除失败时保留当前页面并显示错误。

### FR-007 通知权限与提醒（P1）

- 首次启动不主动请求通知权限。
- 用户首次选择未来复盘日期并点击保存时，若系统需要权限，先显示用途说明，再请求权限。
- 用户拒绝权限后，决策仍然可以保存；页面提示“已保存，但系统提醒未开启”。
- 修改日期时取消旧任务并创建新任务。
- 清除日期时取消旧任务。
- 每个决策最多存在一个提醒任务，唯一键为 `review-$decisionId`。

### FR-008 详情页“当时 / 后来”结构（P1）

详情页按以下顺序展示：

1. 顶部：返回、问题、记录日期、状态。
2. **当时的决定**：背景、候选项、最终选择、在意的事、担心的事、预期结果、判断信心、未来寄语。
3. **后来发生了什么**：复盘数量、每次复盘日期、实际结果、满意度、与预期关系、判断准确处、意外发现、下次注意事项。
4. 操作：编辑、记录结果、删除。

每条复盘必须显示：

- 第几次复盘。
- 复盘日期。
- 距离创建或上次复盘的时间间隔，无法计算时隐藏。

## 7. 页面与信息架构需求

### 7.1 今天

- 展示品牌名、当前日期和低打扰副标题。
- 有待复盘时优先展示待复盘卡片，可展示数量和最近一条。
- 无待复盘但有历史时展示最近决定。
- 无记录时展示空状态、产品价值说明和“记录一个决定”按钮。
- 主 CTA 在底部安全区域内保持可触达。

### 7.2 决定

- 展示全部决策时间线。
- 增加状态筛选：全部、待复盘、已回看、未设置日期。
- 本期至少支持按问题关键词搜索；无结果时展示空结果状态和清除筛选操作。
- 时间线每项展示问题、更新日期、状态和进入详情操作。

### 7.3 我的

- 只展示统计、洞察和决策时间线摘要，不复制“全部决定”的完整列表。
- 统计卡片至少包含：已完成复盘次数、待复盘数量、最常在意主题。
- 每条洞察显示证据数量，例如“来自 5 条记录”。
- 证据不足时不生成洞察，显示“继续记录，积累更多样本”。

## 8. 数据与技术设计

### 8.1 数据模型原则

保持现有 `Decision`、`Choice`、`Review` 模型，不新增远程服务和账号字段。

需要确认并实现：

- 编辑决策时保留原 `createdAt`。
- 更新 `updatedAt`。
- 通过候选项插入返回的真实 ID 重新映射 `selectedChoiceId`。
- 候选项重建必须在同一个 Room transaction 中完成。
- 删除使用级联业务事务，删除提醒先于删除数据库实体。

### 8.2 Repository 接口建议

```kotlin
fun observeAllDecisions(): Flow<List<Decision>>
fun observeDueDecisions(now: Long): Flow<List<Decision>>
fun observeDecision(id: Long): Flow<Decision?>
suspend fun saveDecision(input: DecisionInput): Result<Long>
suspend fun deleteDecision(id: Long): Result<Unit>
suspend fun saveReview(input: ReviewInput): Result<Long>
```

保存逻辑必须将校验、数据库事务和提醒安排拆分为可测试步骤：

1. 清洗并校验输入。
2. 在 Room transaction 中写入决策和候选项。
3. 根据最终选择重新映射 Choice ID。
4. 事务成功后安排或取消提醒。
5. 向 ViewModel 返回唯一 ID 和明确结果。

如果提醒安排失败，不回滚已经成功保存的本地决策；应提示用户“内容已保存，但提醒未安排”，并允许从详情页重试。

### 8.3 ViewModel 状态

创建和复盘 ViewModel 至少暴露：

```kotlin
val saveState: StateFlow<SaveState>
val errorMessage: StateFlow<String?>
```

禁止使用 Composable 内部的普通变量作为唯一业务状态来源。表单草稿可以由页面持有，但保存状态、加载状态和错误状态必须由 ViewModel 管理。

### 8.4 性能与兼容性

- 继续支持 Android API 26+ 和当前 compile/target SDK。
- 1000 条决策以内，列表首次展示应保持可交互。
- 首页和列表使用 LazyColumn，避免大数据量下的整页 Column 渲染。
- 页面支持 360dp 宽度和系统字体放大 1.3 倍。
- 不引入网络依赖，不上传任何用户内容。

## 10. 验收标准

### 核心业务

- [ ] 新用户空数据库启动时只看到空状态，不自动产生演示数据。
- [ ] 只填写问题和一个候选项即可保存。
- [ ] 编辑已复盘决策后仍显示“已回看”。

- [ ] 首次设置未来日期时显示通知用途说明。

- [ ] 修改、清除和删除复盘日期不会残留旧提醒。

- [ ] 决策内容、复盘内容和设备标识不上传远程服务器。

## 12. 成功指标

本期发布后通过埋点或可重复测试观察以下指标：

- 首次记录完成率：进入创建页后成功保存的比例，目标 ≥ 70%。
- 最小流程完成时间：只记录问题和候选项，目标中位数 ≤ 90 秒。
- 保存失败率：本地保存失败次数 / 保存尝试次数，目标 < 1%。
- 重复数据率：相同操作产生重复决策或复盘的比例，目标为 0。
- 复盘完成率：设置复盘日期的决定中完成至少一次复盘的比例，作为后续基线指标。

本地优先产品不得上传用户内容；若未来需要统计，只允许上传不包含决策正文的匿名事件，且必须另行评审隐私方案。

## 13. 上线前未决问题

以下问题不阻塞本期开发，但上线前必须确认：

1. 正式产品是否需要用户主动选择“加载示例数据”的入口？
2. 是否保留“我的”页面中的自我洞察，还是先只展示可解释统计？
3. 搜索是否仅匹配问题，还是同时匹配背景、选项和复盘结果？
4. 用户是否需要导出本地数据作为隐私备份？
5. 通知被系统限制时，是否在详情页提供手动重试入口？
